# ⚙️ 5 Mental Models (5MM) — 核心心智模型

## MM-1. The C++ Object & Memory Model — 對象-記憶體雙層模型

The single most powerful mental model in C++ is the **dual representation of every object**: a *language-level* abstraction (class invariants, access control) layered on a *machine-level* reality (bytes, addresses, layout rules). Stroustrup (1997, *D&E of C++*, §3.3) frames this as "C++'s fundamental principle: what you don't use, you don't pay for"; this principle is sometimes called *Stroustrup's zero-overhead rule* and was reformulated as a final ISO doctrine in Stroustrup (2013, §1.3).

**The five-region process memory layout** (each region has different cost, lifetime, and growth direction):

$$\text{addr}_{\text{stack}} \downarrow \quad \bigg| \quad \bigg| \quad \bigg| \quad \bigg| \quad \uparrow \quad \text{addr}_{\text{heap}}$$

| Region | Growth direction | Lifetime | Typical Size | Allocation cost |
|---|---|---|---|---|
| **Stack** (棧) | ↓ high → low | Function scope | 1–8 MB (Linux default 8 MB; `ulimit -s`) | ~1 ns (single `sub rsp, n`) |
| **Heap** (堆) | ↑ low → high | Manual / smart ptr | Process-limited (≥ RAM) | ~50–500 ns (`malloc`) |
| **BSS** | static | Process | Zero-init globals | 0 (page-fault on demand) |
| **Data** | static | Process | Initialized globals | 0 (mapped at load) |
| **Text** | static | Process | Code (read-only) | 0 (shared pages) |

The **stack size formula** for a function calling depth $d$ with frame $F$:
$$S_{\text{stack}} \;\approx\; d \cdot F_{\text{avg}} \quad \text{where} \quad F_{\text{avg}} \in [64, 4096]\;\text{bytes}$$

A recursive JSON parser at depth $d=10^4$ easily overflows the 8 MB stack — *tail* recursion (Stroustrup 2013, §8.4) and heap-allocated ASTs (Aho, Lam, Sethi & Ullman 2006, *Compilers: Principles, Techniques, and Tools*, §5.3) prevent this.

**Pointer arithmetic with type awareness** (K&R 1978, *The C Programming Language*, §5.4; Stroustrup 2013, §7.2):
$$\text{ptr} + n \;=\; \text{ptr} + n \cdot \text{sizeof}(T) \quad \text{bytes}$$

**Smart pointer cost model** (C++11, ISO/IEC 14882:2011 §20.7; Meyers 2014, *Effective Modern C++*, Items 18–22):

| Smart pointer | Size (64-bit) | Per-copy cost | When to use |
|---|---|---|---|
| `unique_ptr<T>` | 8 B (raw pointer) | 0 (move only) | Single owner (default) |
| `shared_ptr<T>` | 16 B (obj + control block ptr) | ~25 ns atomic `fetch_add` | Shared ownership |
| `weak_ptr<T>` | 16 B | atomic `add` then `lock()` | Break cycles; observers |

Solution: pre-allocate a `std::vector<PointCloud>` and reuse — Knuth (1968) called this *the disciplined use of storage*.

## MM-2. The Type System as a Compile-Time Computation Engine

C++ templates are a **Turing-complete functional language** executed by the compiler (Vandevoorde, Josuttis & Gregor 2017, *C++ Templates: The Complete Guide*, 2nd ed., Ch. 4). Templates perform type erasure *at instantiation*, not at runtime — yielding **zero-cost abstractions** (Stroustrup 2013, §1.3). This was demonstrated empirically by Stepanov (2009, "Fundamentals of Generic Programming," keynote at ICCP), who showed that `std::sort<int*>` produces assembly indistinguishable from hand-rolled `qsort` in identical benchmarks.

**Core template equation** — the substitution mechanism (Stroustrup 2013, §23.2):
$$\text{instantiate}\langle T = U \rangle \;\Longrightarrow\; \text{compile}\bigl(\text{body}[T \mapsto U]\bigr)$$

The number of instantiations grows combinatorially with cross-products of type parameters — a phenomenon Czarnecki & Eisenecker (2000, *Generative Programming*, Ch. 4) call *template instantiation explosion*.

**SFINAE — Substitution Failure Is Not An Error** (ISO C++ standard since C++98; Vandevoorde et al. 2017, §6.4):
$$\text{try substitute} \to \text{if fails} \to \text{silently remove overload from candidate set}$$

**Concepts (C++20)** — declarative constraints replacing SFINAE (Gregor et al. 2017, "Concepts (P0734R2)"):
```cpp
template<typename T>
concept Numeric = std::is_arithmetic_v<T>;

template<Numeric T>
T mean(std::span<const T> data); // constrained, clean error messages
```

**Compile-time computation** (Stroustrup 2013, §10.4):
$$N! = \prod_{k=1}^{N} k \quad \Longrightarrow \quad \texttt{constexpr } N! = \texttt{value} \quad \text{(computed at compile time)}$$

The constexpr general-subexpression-elimination works because $N!$ satisfies the *literal-type* requirement (ISO §7.7).

**Key scholars**:
- Vandevoorde, D., Josuttis, N. M., & Gregor, D. (2017). *C++ Templates: The Complete Guide*, 2nd ed. Addison-Wesley
- Stroustrup, B. (2013). *The C++ Programming Language*, 4th ed., §23 (templates)
- Gregor, D. et al. (2017). "Concepts (P0734R2)." ISO C++ Standardization proposal
- Czarnecki, K. & Eisenecker, U. (2000). *Generative Programming*. Addison-Wesley
- Stepanov, A. (2009). "Fundamentals of Generic Programming." ICCP keynote

**Engineering payoff**: A 6-DOF forward-kinematics template `forwardKinematics<RobotType>(q)` resolves to the exact robot's symbolic Jacobian at compile time — saving microseconds per control cycle in a 1 kHz loop (Spong, Hutchinson & Vidyasagar 2006, *Robot Modeling and Control*, Ch. 3).

## MM-3. STL Container Complexity Model — 容器複雜度心智模型

Every STL container carries a **guaranteed asymptotic profile** documented in the C++ standard (ISO/IEC 14882:2020 §22–24; Josuttis 2012, *The C++ Standard Library*, 2nd ed., Ch. 4–9). The mental model: pick by **dominant operation**, not by intuition.

**Master complexity table** (worst-case; average in subscript):

| Container | Random access | Insert (front/mid/back) | Erase | Search | Memory layout |
|---|---|---|---|---|---|
| `std::vector<T>` | $O(1)$ | $O(n)$ / $O(n)$ / $O(1)_{\text{amort}}$ | $O(n)$ | $O(n)$ | Contiguous, cache-optimal |
| `std::deque<T>` | $O(1)$ | $O(1)$ / $O(n)$ / $O(1)$ | $O(n)$ | $O(n)$ | Segmented contiguous |
| `std::list<T>` | $O(n)$ | $O(1)$ / $O(1)$ / $O(1)$ | $O(1)$ | $O(n)$ | Node-linked, cache-poor |
| `std::array<T,N>` | $O(1)$ | ✗ | ✗ | $O(n)$ | Stack-only, contiguous |
| `std::forward_list<T>` | $O(n)$ | $O(1)$ / $O(1)$ / ✗ | $O(1)$ | $O(n)$ | Singly linked, half-memory |
| `std::unordered_map` | $O(1)_{\text{avg}}$ | $O(1)_{\text{avg}}$ | $O(1)_{\text{avg}}$ | $O(1)_{\text{avg}}$ | Hash buckets, $O(n)_{\text{worst}}$ |
| `std::map` | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | $O(\log n)$ | Red-black tree (Guibas & Sedgewick 1978) |
| `std::priority_queue` | ✗ | $O(\log n)$ push | $O(\log n)$ pop | $O(1)$ top | Vector-as-heap |

**Vector amortized analysis** (Cormen, Leiserson, Rivest & Stein 2009, *CLRS* §17.4 — "Amortized Analysis via Aggregate Method"):
$$\sum_{k=0}^{\log_2 n} 2^k = 2n - 1 \quad \Longrightarrow \quad \text{amortized } O(1) \text{ per push_back}$$

When the vector doubles, one push pays $O(n)$ — but it happens only every $\log_2 n$ pushes, so the average is constant.

**Cache locality model** (Drepper, U. (2007). "What Every Programmer Should Know About Memory." *ACM Queue* 5(7)):
$$\text{Miss penalty}_{\text{L1}} \approx 1\text{ ns}, \quad \text{Miss penalty}_{\text{RAM}} \approx 100\text{ ns}$$

This **100× gap** means that for small $n$, a contiguous `vector` beats `list` even when both are asymptotically $O(n)$.

- Cormen, T. H., Leiserson, C. E., Rivest, R. L., & Stein, C. (2009). *Introduction to Algorithms*, 3rd ed., Ch. 10–13
- Josuttis, N. M. (2012). *The C++ Standard Library*, 2nd ed. Addison-Wesley
- Drepper, U. (2007). "What Every Programmer Should Know About Memory." *ACM Queue* 5(7)
- Musser, G., Derge, G. J., & Saini, A. (2009). *STL Tutorial and Reference*, 3rd ed.

- Sutter, H. & Alexandrescu, A. (2004). *C++ Coding Standards*, Item 76

**Engineering decision rule** (Sutter & Alexandrescu 2004, Item 76):
> "Default to `std::vector`. Reach for another container only when a profiler proves the vector is the bottleneck."

## MM-4. RAII & Deterministic Lifetime — 確定性生命週期模型

**RAII = Resource Acquisition Is Initialization** (Stroustrup 1985, §4.9; formalized in Stroustrup 1997, §16.2). The mental model: bind resource lifetime to *object* lifetime so the compiler's deterministic destructor call becomes your cleanup mechanism. Dijkstra (1968, "GO TO Statement Considered Harmful," *CACM* 11(3)) and Hoare (1974, "Hints on Programming Language Design," *SIGACT*) articulated the deeper principle: control flow should be expressed through *structure*, not through *spooky action* at exception unwinding.

**The invariant equation**:
$$\text{Constructor open} \;\Longleftrightarrow\; \text{Destructor close (always runs at scope exit)}$$

**Three exception-safety levels** (Abrahams, D. (2001). "Exception Safety in Generic Components," in Sutter 2001, *Exceptional C++*, Items 1–10):

| Level | Guarantee | Implementation pattern |
|---|---|---|
| **Basic** | No leak, invariants preserved | Destructors always run |
| **Strong** | Commit-or-rollback | Copy-and-swap idiom (Sutter 2004, Item 12) |
| **No-throw** | Never throws | `noexcept` + move-only |

**The `noexcept` specification** (ISO C++11 §15.4; Meyers 2014, Item 14):
$$f() \texttt{ noexcept} \;\Longrightarrow\; \begin{cases} \text{compiler may elide EH landing pads (saves ~10% code on ARM)} \\ \text{`std::vector` uses move instead of copy during reallocation} \\ \text{enables TCO and devirtualization} \\ \text{move-or-copy decision is binary, not exception-driven} \end{cases}$$

**The "strong guarantee" idiom** (copy-and-swap, Sutter 2004):
$$T_{\text{op}}(s) \;=\; \texttt{copy}(\text{snapshot}) \to \texttt{commit}\bigl(\texttt{swap}(s, \text{snapshot})\bigr)$$
If `commit` throws, the snapshot destructs cleanly and the original state is preserved.

**Key scholars & dates**:
- Stroustrup, B. (1985). *The C++ Programming Language*, 1st ed., §4.9 — coined "RAII"
- Meyers, S. (2001). *Effective C++*, 3rd ed., Items 13, 14, 17 — RAII scope guards
- Sutter, H. (2001). *Exceptional C++*, Items 1–10
- Abrahams, D. (2001). "Exception Safety in Generic Components." *MCC*
- Sutter, H. (2004). *C++ Coding Standards*, Item 12 (copy-and-swap), Item 70 (errors)
- Dijkstra, E. W. (1968). "GO TO Statement Considered Harmful." *CACM* 11(3)
- Hoare, C. A. R. (1974). "Hints on Programming Language Design." *SIGACT News*

**Hardware interface example**:
```cpp
class CANBus {
    int fd_;
public:
    CANBus(const char* dev) : fd_(open(dev, O_RDWR)) { if (fd_<0) throw BusError(); }
    ~CANBus() { if (fd_>=0) close(fd_); }   // always runs
    CANBus(const CANBus&) = delete;
    CANBus(CANBus&& o) noexcept : fd_(o.fd_) { o.fd_ = -1; }
};
```

## MM-5. Concurrency & Memory-Model Mental Model — 並行與記憶體序心智模型

C++11 introduced a **formal memory model** (ISO/IEC 14882:2011 §1.10; Boehm & Adve 2008, "Foundations of the C++ Concurrency Memory Model," *PLDI '08*). Every threading mental model reduces to: *which writes are visible to which reads, and when?* The model was the first major standardization following Lamport's foundational work.

**The fundamental contract** (Lamport 1979, "How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs," *IEEE Trans. Comput.* C-28(9): 690–691):
$$\text{Program order} \subseteq \text{Observe order (per thread)}$$
$$\text{synchronizes-with}(\text{release}, \text{acquire}) \subseteq \text{happens-before}$$

**Six memory orderings** form a *lattice* (ISO C++11 §29.3, ordered from weakest to strongest):

$$M_{\text{relaxed}} \sqsubset M_{\text{consume}} \sqsubset M_{\text{acquire}} \sqsubset M_{\text{release}} \sqsubset M_{\text{acq\_rel}} \sqsubset M_{\text{seq\_cst}}$$

**Acquire-release protocol** for a producer-consumer flag:
$$\text{Producer: } \texttt{store}(\text{data}, \texttt{release});\; \texttt{store}(\text{flag}, 1, \texttt{release})$$
$$\text{Consumer: } \texttt{while}(\texttt{load}(\text{flag}, \texttt{acquire}) == 0);\; \text{use}(\text{data})$$

**False-sharing equation** (Williams 2019, *C++ Concurrency in Action*, 2nd ed., §5.4.4):
$$\text{Cache-line size} = 64\,\text{B} \;\Rightarrow\; \text{false-shared atomics} \in \mathbb{N} \text{ per line} \;\Rightarrow\; \text{ping-pong at } 10\text{-}100\,\text{ns/transfer}$$

Mitigation: align atomics to 64-byte boundaries (`alignas(64)`).

**The cost spectrum** (measured on x86-64 and ARMv8, Boehm 2012, WG21 N2644):

| Order | x86 cost | ARM cost | Use case |
|---|---|---|---|
| `relaxed` | plain `mov` | `dmb ish` if needed | Counters (no visible state) |
| `acquire`/`release` | plain `mov` | `ldar`/`stlr` | Message passing |
| `seq_cst` | `mfence` (or RMW) | `dmb ish` | Default — most portable |

**Key scholars & dates**:
- Lamport, L. (1979). "How to Make a Multiprocessor Computer That Correctly Executes Multiprocess Programs." *IEEE Trans. Comput.* C-28(9): 690–691
- Boehm, H.-J. & Adve, S. V. (2008). "Foundations of the C++ Concurrency Memory Model." *PLDI '08*
- Boehm, H.-J. (2012). "Memory Model synchronization effects." WG21 N2644
- Williams, A. (2019). *C++ Concurrency in Action*, 2nd ed., Ch. 5–6
- ISO/IEC 14882:2011 §1.10, §29.3

**Engineering application**: A 1 kHz robot control loop reads IMU samples written by a 200 Hz ISR. Using `seq_cst` for the sample flag costs ~20 ns per loop on ARM Cortex-A53 vs ~5 ns for `acquire`/`release` — measured on a BeagleBone Black (Williams 2019, §5.3.4).

# 🔥 3 Fundamental Disagreements (3DG) — 根本分歧

## DG-1. The "Zero-Cost Abstractions" Debate — 零成本抽象之辯

| Position | Argument | Champion(s) |
|---|---|---|
| **A: Yes, zero-cost.** | Templates & `inline` produce assembly identical to hand-coded C; abstractions vanish at compile time. | Stroustrup (2013, §1.3); Stepanov (2009, "Fundamentals of Generic Programming") |
| **B: No, hidden costs.** | Each abstraction layer adds compile time, binary size, cognitive load; "what you don't use, you don't pay for" is a half-truth (you *do* pay in metadata even if not in registers). | Muratori (2014, "The Cost of Abstractions," *MollyRocket forum*); Hickey (2011, "Simple Made Easy," *Strangeloop*) |

**Tension**: C++'s design philosophy ("don't pay for what you don't use" — Stroustrup 1997, §4.1) implies that abstractions should compile away. However, complex template metaprograms can inflate binary size by 5–10× (Abrahams 2004, "Compile-Time Combinatorics," BoostCon), and exceptions add per-function EH tables (~5–20 KB overhead per translation unit — Google benchmark, 2014). Even more subtly, every `#include <iostream>` pulls 12,000 lines of header even when you call only `std::cout::operator<<`.

**Resolution heuristic**: Profile before abstracting. For 1 kHz control loops, the answer is "yes, zero-cost"; for library code, "use abstractions; trust the compiler." (Garbage Collection was famously rejected for C++ by Stroustrup (1997, §5.4) precisely because it would violate "don't pay for what you don't use.")

## DG-2. Raw Pointers vs. Smart Pointers — 指標哲學之爭

| Position | Argument | Champion(s) |
|---|---|---|
| **A: Smart pointers everywhere.** | Eliminate leak/dangling-pointer bugs by construction; modern C++ (C++11+) style. | Meyers (2014, *Effective Modern C++*, Items 18–22); Sutter (2013, "Raw Pointers, Raw Pointers, Raw Pointers" — nuanced; mostly agrees) |
| **B: Raw pointers for observation, smart for ownership.** | A raw pointer is a *non-owning view*; using `shared_ptr` for every reference destroys performance and confuses semantics. | Hinnant, H. (2018, "unique_ptr, shared_ptr, weak_ptr — How to Choose," ISO WG21); Facebook Folly style guide |

**Tension**: School A sees any raw `new` as a code smell (Meyers 2014, Item 18: "Prefer smart pointers to raw pointers"). School B argues that ownership and observation are *different* concepts and should be syntactically distinguishable (Hinnant is the lead designer of `std::move`, `unique_ptr`, and `<chrono>` in C++11).

**Resolution heuristic** (Stroustrup, Sutter, ISO C++ Core Guidelines, R.10–R.32):
- `T*` → non-owning, possibly null (observation only)
- `T&` → non-owning, never null (reference)
- `unique_ptr<T>` → single owner (movable, not copyable)
- `shared_ptr<T>` → shared owner (last copy destroys)

## DG-3. Exceptions vs. Error Codes — 錯誤處理之爭

| Position | Argument | Champion(s) |
|---|---|---|
| **A: Exceptions for errors.** | Separate error path from happy path; destructors auto-cleanup; the standard library uses them. | Stroustrup (1997, §16); Sutter (2004, *C++ Coding Standards*, Item 70); Josuttis (2012) |
| **B: Error codes / `std::expected` for errors.** | Exceptions are zero-cost on the happy path but cause code bloat, hidden control flow, and are *forbidden* in hard real-time (e.g., AUTOSAR C++14, rule A15-4-1). | AUTOSAR (2017, *Guidelines for the use of C++14 in critical and safety-related systems*); Mozilla (2015); Linus Torvalds (2007, LKML, "…the whole C++ exception handling thing is fundamentally broken") |

**Tension**: Exceptions integrate beautifully with RAII but introduce "spooky action at a distance" (a `throw` deep in a dependency surfaces 12 stack frames up). Real-time automotive and aerospace standards (DO-178C, AUTOSAR) **prohibit** dynamic exceptions because the unwinder's runtime cost is *unbounded* — making worst-case execution time (WCET) analysis intractable.

**Resolution heuristic** (modern middle ground, P0323R11, Sutter 2018; Hinnant, Brand, et al. 2021):
- Use `std::expected<T, Error>` (C++23) for recoverable failures
- Reserve `throw` for genuinely exceptional, unrecoverable events
- In embedded/real-time: error codes only — no exceptions, no RTTI, no virtual

# 🎯 10 Probing Questions with Detailed Answers (10Q)

### Q1. Why does a `std::vector` typically outperform `std::list` even when both have the same Big-O complexity?

**Answer**: Big-O notation describes asymptotic behavior as $n \to \infty$, but real engineering operates at *finite* $n$ (typically $n < 10^4$ for sensor data). The decisive cost in this regime is **cache behavior**. A `std::vector<T>` stores elements contiguously, so loading element $i$ brings elements $i, i+1, \ldots, i+7$ (a 64-byte cache line, Drepper 2007) into L1 simultaneously — a *spatial prefetcher* win. A `std::list<T>` stores each node separately, requiring a fresh cache miss (~ 100 ns on x86, Drepper 2007, §6) per dereference of `next`. For `vector::push_back` (amortized $O(1)$, CLRS §17.4) at 1000 elements, total memory traffic ≈ 8 KB (fits in L2), whereas `list` traverses 1000 nodes × ~40 bytes = 40 KB of random pointers, evicting useful cache lines and incurring cache misses on each hop. Even more subtly, `std::list` node allocation requires 1000 calls to `operator new`, each ~50–500 ns — for 1000 nodes, that's 50–500 μs pure allocator cost vs. vector's one or two reallocations (Meyers 2014, Item 16). The rule (Sutter & Alexandrescu 2004, Item 76) is: **default to `std::vector`**; reach for `std::list` only when you have measured iterator-invalidation or middle-insertion bottlenecks at scale $n > 10^5$ where the asymptotic wins become real. For a robot IMU buffer of 1000 samples at 1 kHz, vector is *always* faster — by a factor of 5–20× in microbenchmarks (Malinen 2020, ROS2 performance report).

### Q2. How does `std::move` work, and why is it "free" while copying is expensive?

**Answer**: Move semantics (C++11, ISO/IEC 14882:2011 §12.8) exploit the fact that after a source object is no longer needed, its **resources can be transferred** rather than duplicated. A `std::move(x)` does not move anything — it is a `static_cast<std::remove_reference_t<T>&&>(x)` that yields an *rvalue reference*, signaling "this object is about to die, you may steal its guts." A move constructor performs a shallow pointer swap:
```cpp
class Buffer {
    T* data_; size_t n_;
public:
    Buffer(Buffer&& o) noexcept : data_(o.data_), n_(o.n_) {
        o.data_ = nullptr; o.n_ = 0;  // leave the source empty but valid
    }
};
```
The cost is three pointer assignments: **O(1)**. Compare to a copy constructor which must allocate new memory and copy each element: $O(n)$ time plus $O(n)$ memory traffic. The compiler can elide the move entirely via **copy elision** (RVO/NRVO, ISO §12.8.31): when a function returns a local by value, the caller's storage is reused — the move never appears in assembly (Stroustrup 2013, §3.3.3). **Engineering note**: marking move operations `noexcept` is critical — otherwise `std::vector` falls back to copying during reallocation (ISO §22.3.1; Meyers 2014, Item 14). The cost ratio can be summarized as:
$$\frac{T_{\text{copy}}}{T_{\text{move}}} \;\approx\; \frac{n \cdot t_{\text{copy-elem}}}{3 \cdot t_{\text{assign}}} \;\approx\; \frac{n}{3}$$
For $n = 10^6$ doubles, copy is ~300,000× slower than move (Stroustrup 2013, §5.2).

### Q3. What is the vtable, and how does it enable polymorphism?

**Answer**: A virtual function table (vtable) is a **per-class array of function pointers** constructed by the compiler; each polymorphic instance carries a hidden pointer (`vptr`) to its class's vtable (Stroustrup 1997, §3.5; Lippman 1996, *Inside the C++ Object Model*, Ch. 4; Mangham & Stroustrup 2017, *Itanium C++ ABI* §2.4). The dispatch equation is:
$$\text{obj} \xrightarrow{+\texttt{sizeof}(vptr)} \text{vptr} \to \text{vtable}[\text{slot}_i] \to \text{actual function}$$
This indirection enables runtime selection of the correct override — a `Sensor*` pointer can call the right `read()` whether the actual object is `IMU` or `Lidar`. **Cost**: one pointer load + one indirect call (~5 ns on modern x86, more on ARM with branch prediction misses; see Drepper 2007 §6.5). **Diamond inheritance** complicates this: without virtual inheritance, a `Robot` derived from both `Mover` and `Communicator` (both from `Device`) carries *two* `Device` subobjects, and `Robot* → Device*` is ambiguous. **Virtual inheritance** (Stroustrup 1997, §4.2) inserts a `vbase_offset` into the layout so all paths to `Device` share one subobject — at the cost of slightly more complex initialization order (most-derived class constructs virtual bases, ISO §12.6.2). The combined vtable layout for a diamond uses *virtual table groups* (Itanium ABI). **Engineering trade-off** (Gamma et al. 1994, *Design Patterns*, Ch. 5): composition + interface is usually preferred to deep inheritance trees; vtables add ~8 bytes per polymorphic class, two pointer loads per virtual call.

### Q4. Explain the rule of 5 / rule of 3 / rule of 0.

**Answer**: The **Rule of 3** (Meyers 2001, *Effective C++* 3rd ed., Item 27) states: if a class requires any of (a) destructor, (b) copy constructor, (c) copy assignment operator, it almost certainly requires all three — because the need signals manual resource management, and the absence of any of the three risks resource leaks or double-frees. With C++11, the **Rule of 5** (Meyers 2014, *Effective Modern C++*, Item 17) extends this: add (d) move constructor and (e) move assignment operator, because asymmetric move support degrades to copying silently when a move overload is missing. The **Rule of 0** (Meyers 2014, Item 4; Sutter 2014, *CppCon talk*) flips the advice: prefer designs with *no manual resource management at all* — use RAII wrappers (`std::vector`, `std::string`, `std::unique_ptr`) so the compiler-generated defaults are correct. **Engineering translation**: a `Matrix` class holding an `std::vector<double>` needs **zero** custom members — the default destructor, copy, and move all do the right thing because they delegate to `std::vector`. Only when wrapping raw C resources (file descriptors, sockets, C library handles, hardware bus IDs) do you need Rule-of-5. As Alexandrescu (2001, *Modern C++ Design*, Ch. 5) showed, the *Policy-Based Design* idiom can wrap raw resources into typed smart pointers so user code never manages them by hand.

### Q5. How does `std::variant` differ from inheritance-based polymorphism, and when to use each?

**Answer**: `std::variant<T1, T2, ...>` (ISO C++17, P0088R3; Josuttis 2019, *C++17*, Ch. 4) is a **type-safe union** with a discriminator. It is *closed*: the set of alternative types is fixed at compile time, and the visitor pattern (`std::visit`) replaces virtual dispatch. Inheritance-based polymorphism is *open*: new derived classes can be added without touching existing code (Open-Closed Principle, Meyer 1988, *Object-Oriented Software Construction*, Ch. 3; Gamma et al. 1994, *Design Patterns*). **Performance**: `variant` has zero-overhead storage (it's a union + small discriminator byte); no vtable lookup, no heap allocation. Inheritance requires a heap allocation (unless using `std::make_unique` with the right deleter), plus vtable dereferencing. **Trade-offs**:
- `variant` → closed sets (states of a state machine: Idle/Running/Stopped; AST nodes in a compiler)
- Inheritance → open sets (plugin systems; sensor types added by third-party developers)
- Stateful monorepo state machines (5–10 states) → use `variant`; user-extensible sensor pipelines → use inheritance with `std::unique_ptr<Sensor>` (Hinnant 2018).
- The `std::visit` macro makes exhaustive visitor checks compile-time: an unhandled alternative is a compile error.

### Q6. What is SFINAE and how does it differ from C++20 concepts?

**Answer**: SFINAE = **Substitution Failure Is Not An Error** (ISO C++ standard since 1998; Vandevoorde et al. 2017, §6.4). When the compiler substitutes template parameters, if substitution produces an ill-formed type, the candidate is *silently* removed from overload resolution — no error is raised. This is the original mechanism for compile-time type traits, e.g.:
```cpp
template<typename T>
auto serialize(T& t) -> decltype(t.serialize(), void()) { t.serialize(); }
template<typename T>
auto serialize(T& t) -> decltype(t.to_string(), void()) { t.to_string(); }
```
SFINAE produces *legendary* terrible error messages — a failed substitution can cascade through pages of "instantiated from here" stacks. **Concepts (C++20, P0734R2, Gregor 2017)** replace SFINAE with declarative constraints:
```cpp
template<Serializable T>
void serialize(T& t);
```
Benefits: (1) error messages name the *violated constraint* directly; (2) clearer intent; (3) better overload resolution via concept *subsumption* (ISO §17.6.5). The mental model: **SFINAE is a hack; concepts are the principled design** (Stroustrup 2018, *A Tour of C++*, 2nd ed., §8.4). Concepts were voted into C++20 by the WG21 committee in July 2017 after a decade of design work (initiated by Stroustrup, Sutton & Dos Reis in 2009 N2914).

### Q7. Why is `noexcept` so important for performance?

**Answer**: `noexcept` (ISO C++11 §15.4; Meyers 2014, Item 14) is a contract: this function **never throws**. The optimizer uses this contract in three ways:
1. **Devirtualization**: the compiler can omit the implicit EH landing pad, reducing code size per function by ~10% on ARM (Williams 2019, §5.5.3).
2. **`std::vector` reallocation strategy**: when reallocating, vector *must* move each element. If the move is not `noexcept`, vector falls back to *copying* (ISO §22.3.1) — destroying your performance. This single annotation can change a 10× slowdown into 0× overhead.
3. **`std::swap` is unconditionally `noexcept`**: conditional `noexcept` propagates through templates via the `std::is_nothrow_*_constructible` trait (ISO §20.7).

The cost spectrum (measured on x86-64, GCC 12):
- Function with `noexcept` and no throws: identical to a C function
- Function without `noexcept`: +5–20 KB EH table per translation unit (Sutter 2005, *C/C++ Users Journal*)
- Function with `noexcept(false)`: identical to non-noexcept

For a high-frequency template like `std::function<>` dispatch, `noexcept` propagation can yield 20–40% speedup (Stroustrup 2013, §13.8.2). In embedded contexts where exceptions are disabled (`-fno-exceptions`), `noexcept` is the *default* and saves the "abort" prologue entirely.

### Q8. How does RAII enable thread-safe resource management without manual locking?

**Answer**: RAII binds resource lifetime to scope, so **acquisition and release are temporally coupled to constructor and destructor calls** (Stroustrup 1997, §16.2). For mutexes, `std::lock_guard<std::mutex> lock(mtx)` acquires on construction and *unconditionally* releases on destruction — even when an exception unwinds the stack:
```cpp
void transfer(Account& from, Account& to, double amt) {
    std::lock_guard lk1(from.mtx);
    std::lock_guard lk2(to.mtx);   // ⚠️ potential deadlock if two threads call in reverse order
    from.balance -= amt;
    to.balance += amt;
}
```
The `lock_guard` cannot "forget" to release, regardless of how the function exits. For more sophisticated cases, `std::unique_lock` provides deferred locking and is required for `condition_variable`. **Deadlock prevention** uses `std::scoped_lock` (C++17), which acquires multiple mutexes atomically using the deadlock-avoidance algorithm (ISO §30.4.1.3, based on Dijkstra's banker-algorithm like partial ordering). **The deeper principle**: by making resource management an *automatic consequence of normal control flow*, RAII eliminates an entire class of bugs (Sutter & Alexandrescu 2004, Items 13, 14). For files: `std::ofstream` closes via destructor (Josuttis 2012, Ch. 15); for memory: `std::unique_ptr` deletes via destructor (Meyers 2014, Item 18); for threads: `std::thread` either joins or detaches before destruction (ISO §30.3.1.3 — terminating program if neither, in contrast to `std::jthread` (C++20) which automatically joins).

### Q9. Why does `std::shared_ptr` have a 2× size overhead, and when is it worth it?

**Answer**: `std::shared_ptr<T>` internally holds **two pointers**: one to the managed object, one to a *control block* containing the reference count, weak count, and custom deleter (ISO §20.7.2.2; Meyers 2014, Item 19). On 64-bit, this is 16 bytes vs. 8 for `unique_ptr<T>`. Additionally, every refcount operation is an atomic `fetch_add`/`fetch_sub` — ~25 ns uncontended, but with cache-line bouncing across cores it can cost 100+ ns (Williams 2019, §5.2.5). The control block is heap-allocated separately from the object. **`make_shared<T>(...)` optimizes this** by allocating both object and control block in one allocation (ISO §20.7.2.5; saves ~50 ns and 16 bytes). **Worth it when**: (1) shared ownership is genuinely needed (multiple owners with independent lifetimes); (2) the cost is small relative to the operation time (e.g., a robot sensor shared between logging and control threads — the cost is dwarfed by sensor read time). **Not worth it when**: (1) there is a clear single owner (use `unique_ptr`); (2) you only need non-owning observation (use raw pointer or `weak_ptr`); (3) you have a hot loop incrementing the count. **Anti-pattern**: `shared_ptr` for parent-child relationships — use `unique_ptr` from parent to child, and a raw `T*` from child back to parent (Hinnant 2018). **Cycle avoidance**: every bidirectional relationship must use `weak_ptr` on at least one side (Meyers 2014, Item 20) — otherwise the strong-count is permanently ≥ 2.

### Q10. What is the difference between `constexpr`, `const`, and `#define`, and when to use each?

**Answer**:
- **`#define X 42`** — preprocessor macro (Stroustrup 2013, §12.6). Blind text substitution before the compiler sees the code. No type, no scope, no debugger visibility, no respect for namespaces. *Avoid in modern C++* (Meyers 2014, Item 3). Still useful for include guards and conditional compilation: `#ifdef DEBUG`, `#pragma once`.
- **`const int X = 42;`** — runtime constant with type and scope. Address may exist; can be passed by reference. Use for read-only values whose initializer is not a constant expression.
- **`constexpr int X = 42;`** (C++11, generalized in C++14/17/20) — **compile-time constant** (Stroustrup 2013, §10.4). The compiler evaluates the initializer at compile time; the symbol may have *no runtime address at all*. Use for array sizes, template arguments, and `static_assert`s. C++14 allows local mutation inside the function body; C++20 allows `constexpr` virtual functions, `std::vector`, and `std::string` (ISO C++20 §9.2.6).

The hierarchy of "constness" in C++20 (set inclusion):
$$\text{read-only} \supset \text{runtime const} \supset \text{compile-time const} \supset \text{literal type}$$

**Decision rules**:
- `#define` → include guards, `#ifdef`, platform-specific macros
- `const` → function parameters, member functions that don't modify state
- `constexpr` → anything computable at compile time (math constants, small lookup tables, parametric array bounds)
- `enum class` → typed enumerations replacing `#define` flags (Sutter & Alexandrescu 2004, Item 26)
- `std::string_view` (C++17) or `std::format` (C++20) → for printf-style format strings — `constexpr` validated

## DD-1. The C++ Object Memory Layout / C++ 對象記憶體佈局

**English**: Every C++ object has two layouts: a **language-level view** (member functions, access control, virtual dispatch) and a **machine-level view** (bytes in memory, vptr offset, padding). The compiler is responsible for translating between them, and the standard guarantees only the *observable* layout (ISO §6.7, §10, §12). For non-virtual classes, the layout is: (1) base class subobjects first, in declaration order; (2) non-static data members, in declaration order with possible padding for alignment; (3) no tail padding required. For a class with a `virtual` function, a hidden `vptr` is inserted (typically at the beginning, Itanium C++ ABI §2.4.1; Lippman 1996, Ch. 4), pointing to the class's vtable. With multiple inheritance, the vptr is placed before each base subobject that introduces new virtual functions. With virtual inheritance, a shared `vbase_offset` array is added (Mangham & Stroustrup 2017).

**Equation (sizeof model, single inheritance)**:
$$\text{sizeof}(\text{Derived}) = \text{sizeof}(\text{Base}) + \sum_i \text{sizeof}(m_i) + \text{alignment padding}$$

**Alignment rule** (Itanium ABI §2.1):
$$\text{offset}(m_i) \equiv 0 \pmod{\text{alignof}(m_i)}$$

**Concrete example**:
```cpp
class Base    { int a; };                       // sizeof = 4
class Derived : public Base { int b; };         // sizeof = 8
class Virtual { int v; virtual void f(); };     // sizeof = 16 (vptr + int + padding)
class Diamond : public A, public B {};         // sizeof = sum of A and B (no sharing)
class VirtDiamond : public virtual A, public virtual B {}; // sizeof < sum (shared)
```

**Engineering application to robotics**: When marshalling structs for hardware protocols (e.g., CAN bus messages, FPGA register maps), use `#pragma pack(1)` or `__attribute__((packed))` to disable padding. But first check the hardware spec — many MCUs (STM32, ESP32) require *natural* alignment, and unaligned access traps on some architectures (ARM Cortex-M3 §3.5, "Faulty unaligned access"). The trade-off equation:
$$T_{\text{marshalled}} \;\approx\; n_{\text{packets}} \cdot (T_{\text{struct copy}} + T_{\text{padding shift}})$$

**中文**: C++ 對象有兩種佈局：**語言層級視圖**（成員函數、訪問控制、虛擬分派）和**機器層級視圖**（記憶體中的位元組、vptr 偏移、填充）。編譯器負責兩者之間的轉譯，標準只保證**可觀察**的佈局（ISO §6.7、§10、§12）。對於非虛擬類別，佈局規則為：（1）基礎類別子物件首先按宣告順序排列；（2）非靜態資料成員按宣告順序排列，可能有對齊填充；（3）尾部填充非必需。對於含 `virtual` 函數的類別，隱藏的 `vptr`（通常在開頭，Itanium C++ ABI §2.4.1）指向該類別的 vtable。多重繼承時，每個引入新虛函數的基礎子物件前都會插入 vptr。虛擬繼承時，會加入共享的 `vbase_offset` 陣列（Mangham & Stroustrup 2017；Lippman 1996, 第 4 章）。

**方程式（sizeof 模型，單一繼承）**：
$$\text{sizeof}(\text{Derived}) = \text{sizeof}(\text{Base}) + \sum_i \text{sizeof}(m_i) + \text{對齊填充}$$

**機器人工程應用**：當為硬體協議（例如 CAN bus 訊息、FPGA 暫存器映射）序列化結構時，使用 `#pragma pack(1)` 或 `__attribute__((packed))` 禁用填充。但請先檢查硬體規格——許多 MCU（STM32、ESP32）要求自然對齊，某些架構（ARM Cortex-M3 §3.5）對未對齊存取會觸發 fault。

## DD-2. Move Semantics and Perfect Forwarding / 移動語義與完美轉發

**English**: Move semantics exploit the **lifetime contract**: an rvalue reference (`T&&`) binds to objects that are about to be destroyed, so their resources may be "stolen" rather than copied. The compiler can elide moves entirely via copy elision (RVO/NRVO, ISO §12.8.31) when returning a local by value. Perfect forwarding (Vandevoorde et al. 2017, §6.1; Stroustrup 2013, §28.4 — "universal references") uses `T&&` parameter with `std::forward<T>(t)` to preserve the *value category* of an argument as it passes through forwarding references — essential for factory methods:
```cpp
template<typename T, typename... Args>
std::unique_ptr<T> make(Args&&... args) {
    return std::unique_ptr<T>(new T(std::forward<Args>(args)...));
}
```
The **reference collapsing rules** (ISO §8.3.2.6) are:
$$T\& \& \to T\&, \quad T\& \&\& \to T\&, \quad T\&\& \& \to T\&, \quad T\&\& \&\& \to T\&\&$$

Combined with template argument deduction, `Args&&` binds to either lvalue or rvalue, then `std::forward<Args>` recovers the original category via the collapse rules.

**Performance equation** (Stroustrup 2013, §5.2):
$$T_{\text{move}}(n) \approx 3 \cdot t_{\text{assign}} \quad \text{vs} \quad T_{\text{copy}}(n) = n \cdot t_{\text{copy element}}$$
$$\frac{T_{\text{copy}}}{T_{\text{move}}} = \frac{n \cdot t_{\text{copy}}}{3 \cdot t_{\text{assign}}} = \frac{n}{3} \quad \text{(asymptotic factor for } n \gg 1 \text{)}$$

**Extension to perfect forwarding costs** (Williams 2019, §9.2): a perfect-forwarding constructor invocation is *zero-overhead* (resolved at compile time to the right overload); a hand-rolled virtual dispatch via `clone()` would incur at least one vtable lookup (~5 ns).

**中文**: 移動語義利用**生命週期契約**：右值引用 (`T&&`) 綁定到即將銷毀的對象，因此其資源可以被「偷取」而非複製。當按值返回一個區域變量時，編譯器可以通過**複製省略**（RVO/NRVO，ISO §12.8.31）完全省略移動操作。完美轉發（Vandevoorde et al. 2017, §6.1；Stroustrup 2013, §28.4——「通用引用」）使用 `T&&` 參數搭配 `std::forward<T>(t)` 在轉發引用過程中保留參數的值類別——對於工廠方法等包裝函數至關重要。

**引用折疊規則**（ISO §8.3.2.6）為：
$$T\& \& \to T\&, \quad T\& \&\& \to T\&, \quad T\&\& \& \to T\&, \quad T\&\& \&\& \to T\&\&$$

**性能方程式**：
$$T_{\text{移動}}(n) \approx 3 \cdot t_{\text{assign}} \quad \text{vs} \quad T_{\text{複製}}(n) = n \cdot t_{\text{copy element}}$$
$$\frac{T_{\text{複製}}}{T_{\text{移動}}} = \frac{n}{3} \quad \text{（} n \gg 1 \text{ 時的漸近因子）}$$

## DD-3. Concurrency Memory Model / 並行程式設計的記憶體模型

**English**: C++11 introduced the first standardized memory model for a mainstream language (Boehm & Adve 2008, "Foundations of the C++ Concurrency Memory Model," *PLDI '08*). The model is based on Lamport's (1979) partial-order formulation: each thread has a program order; *synchronizes-with* edges across threads establish total order; `release`/`acquire` ensures that writes before `release` are visible to reads after `acquire` of the same atomic location. Six memory orders form a lattice (ISO §29.3):
$$M_{\text{relaxed}} \sqsubseteq M_{\text{consume}} \sqsubseteq M_{\text{acquire}} \sqsubseteq M_{\text{release}} \sqsubseteq M_{\text{acq\_rel}} \sqsubseteq M_{\text{seq\_cst}}$$
`seq_cst` provides a single total order across all threads (the strongest guarantee, default). **Producer-consumer pattern**:
```cpp
std::atomic<int> flag{0};
Data payload;
// producer thread
payload.prepare();
flag.store(1, std::memory_order_release);
// consumer thread
while (flag.load(std::memory_order_acquire) == 0) spin();
payload.use();  // safe: sees all of producer's prior writes
```
On x86-64, `acquire`/`release` compiles to plain `mov` (TSO); on ARM, to `ldar`/`stlr`. Performance difference: x86 ≈ 0%, ARM ≈ 5% per atomic op; compared to `seq_cst` (which needs `mfence` on x86), `acquire`/`release` is 2–3× faster (Williams 2019, §5.3.3).

**Lock-free counter** example:
$$N_{\text{inc}} =
